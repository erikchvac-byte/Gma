# Architecture Decision Record — Gma's Helper

## Overview

Gma's Helper (working title; BMad project name: "Happy") is a single-page web app that shows active cannabis happy-hour deals within a user-set road-distance radius from the user's location. Each listing shows miles to the shop and a gas-cost-vs-savings calculation. No browsing, no discovery — just "is this deal worth the drive, right now?"

**Status:** Implementation code-complete (2026-06-13). All four epics done and Epic 4 retrospective complete — Epic 1 (Foundation & Data Layer, 1.1–1.3), Epic 2 (Core Deal Experience, 2.1–2.6), Epic 3 (Gas Cost Accuracy, 3.1–3.2), Epic 4 (Live Deal Data via Scraper, 4.1–4.3). Caveat: the app is code-complete but **data-complete for only 1 of 4 dispensary sources** today — `remedy-tulalip` (plain HTML) is live; the three Dutchie sources (`the-joint-everett`, `jet-cannabis-everett`, `kush21-everett-evergreen`) stay Stale until the 4.3 live pass runs the Python Scraper service and resolves the `jet`/`kush21` embed ids. R&D validation begins after that pass + a real `EIA_API_KEY`.
**Owner:** Erik (solo founder), Marysville WA area.

## Architecture Decisions

### ADR-001: Lightweight Single-Page Web App (no native app)
**Status:** Accepted
**Date:** 2026-06-08
**Context:** Cannabis apps face app-store gatekeeping — Google Play bans cannabis-sale-facilitating apps outright (enforced as of 2025-2026); Apple allows licensed dispensary apps but with geo-restrictions. Texas's App Store Accountability Act (effective 2026-01-01) adds age-verification burdens.
**Decision:** Build as a lightweight browser-based single-page web app. No native mobile app, no app-store presence.
**Rationale:** Sidesteps Google's outright ban and emerging age-verification law entirely. Accessible on any device via browser.
**Consequences:** No push notifications, no app-store discovery. Must be mobile-responsive. Hosting/deployment simpler than native.
**Testing:** N/A at this stage.

### ADR-002: Road-Distance Routing (not straight-line radius)
**Status:** Superseded by ADR-011
**Date:** 2026-06-08
**Context:** User explicitly specified 50-road-miles from zip 98270 (Marysville, WA), excluding destinations requiring ferry crossings (Olympic Peninsula, Bremerton).
**Decision:** Use driving-route distance, not straight-line/as-the-crow-flies radius math.
**Rationale:** Straight-line radius would include unreachable destinations across Puget Sound. Road-distance accurately reflects "is this worth the drive."
**Consequences:** Requires a routing/driving-distance API (meaningfully costlier and more complex than a naive geo-radius filter). Need to evaluate API options (Google Maps Routes API, OSRM, etc.) during architecture phase.
**Testing:** Validate by comparing selected WA dispensary addresses against expected include/exclude results.
**Superseded by:** ADR-011 (hardcoded JSON lookups eliminate the routing API entirely for R&D).

### ADR-003: Gas-Cost Calculator — fueleconomy.gov API + Hardcoded National MPG
**Status:** Accepted (refined by ADR-013); **default-MPG half retired by ADR-055** (2026-06-26) — vehicle-precision mode via fueleconomy.gov retained, no national-average default
**Date:** 2026-06-08 / Refined 2026-06-09
**Context:** Core differentiator is the gas-cost-vs-savings comparison. Need vehicle MPG data.
**Decision:** Default MPG is hardcoded at 28 (US fleet average) — see ADR-013. Optional precision mode via fueleconomy.gov public API (Year/Make/Model cascading dropdowns, persisted in browser localStorage). fueleconomy.gov API returns XML; client must send `Accept: application/json` header.
**Rationale:** fueleconomy.gov is a free US government API with proper endpoints intended for third-party use — no scraping, no cost, no ToS risk. The default path requires zero user setup.
**Consequences:** Dependency on fueleconomy.gov availability for precision mode. Fallback: show error in dropdown, Gas Cost falls back to nationalMpg silently.
**Testing:** Verify fueleconomy.gov API returns expected MPG values for known Year/Make/Model combinations. Verify localStorage persistence across sessions.

### ADR-004: Scrape/Aggregate for Deal Sourcing
**Status:** Accepted (with known open risk)
**Date:** 2026-06-08
**Context:** No centralized real-time deal feed exists for cannabis dispensaries. Deals live on individual dispensary websites, SMS clubs, and Instagram — fragmented.
**Decision:** Scrape and aggregate from publicly available dispensary websites and menus. No manual curation, no dispensary self-submission at launch.
**Rationale:** Only feasible solo-founder approach at launch. Keeps the system independent of dispensary cooperation.
**Consequences:** Open risks — (1) ToS/legal exposure from scraping dispensary sites; (2) operational fragility when sites change layout; (3) data freshness challenges. These must be addressed in architecture work: monitoring for breakage, stale-data fallbacks, legal/ethics position on scraping cannabis retail sites specifically.
**Testing:** Accuracy check — small test group (Erik, wife, possibly a friend) verifies displayed deals match real-world deals when they walk in the door.

### ADR-006: Own-Site Crawling Only for v1 (no aggregator scraping)
**Status:** Accepted
**Date:** 2026-06-08
**Context:** Pre-PRD crawl spike (2026-06-08) confirmed ~60% of area dispensaries serve deal data as plain crawlable HTML. Weedmaps/Leafly deal detail requires JS rendering or private API access. Dispensaries using third-party menu subdomains exclusively have no crawlable own-site deal data.
**Decision:** v1 scrapes own-site HTML only. Weedmaps/Leafly deferred to Phase 2. Dispensaries without crawlable own-site deal data excluded from v1 Coverage Zone.
**Rationale:** Simplest viable approach for R&D validation. Avoids JS rendering dependency and aggregator ToS exposure.
**Consequences:** Coverage is ~60% of area dispensaries. Remaining ~40% excluded until Phase 2. Each new dispensary requires a manually written parser.
**Testing:** Spike confirmed Wild Seed Wellness, Remedy Tulalip, Hangar 420 are crawlable. Parser accuracy validated by test-group trips.

### ADR-007: Happy Hours Primary, Daily Deals Secondary
**Status:** Accepted
**Date:** 2026-06-08
**Context:** Spike found two deal archetypes: time-windowed Happy Hours (e.g., Remedy Tulalip 7–8am, Hangar 420 9pm–close) and all-day Daily Deals (e.g., Wild Seed Wellness brand deals).
**Decision:** Feed surfaces Happy Hours first (sorted by time remaining), then Daily Deals (sorted by discount % descending). Both types are shown; Happy Hours are the priority signal.
**Rationale:** Time-windowed deals are higher-urgency; they expire. Daily Deals fill the feed when no Happy Hours are active.
**Consequences:** Scraper must classify deals by type. Happy Hours without parseable time windows fall back to Daily Deal classification.
**Testing:** Verify sort order and classification in feed during R&D.

### ADR-008: Fixed Origin Point at Zip 98270 for v1 (no user GPS)
**Status:** Accepted (assumption — not explicitly confirmed by Erik)
**Date:** 2026-06-08
**Context:** All Road Distance and Gas Cost calculations require a starting point. Browser geolocation would improve accuracy for users not in Marysville but adds complexity.
**Decision:** Origin fixed at zip 98270 centroid for v1. No browser GPS/geolocation used.
**Rationale:** All R&D test users are in Marysville. Eliminates geolocation permission UX and simplifies routing calls. Revisit if concept validates beyond the local test group.
**Consequences:** Gas Cost estimates are inaccurate for users not in Marysville. Acceptable at R&D scale.
**Testing:** N/A — decision is a simplification for R&D.

### ADR-009: Side-by-Side Discount Display (not computed Net Savings dollar figure)
**Status:** Accepted
**Date:** 2026-06-08
**Context:** PRD authoring revealed deals are published as percentages (e.g., "35% off"), not dollar amounts. Computing a dollar Net Savings requires knowing the user's intended spend, which is unknown.
**Decision:** v1 shows "X% off — $Y to get there" side by side (Discount Display) rather than a collapsed Net Savings number.
**Rationale:** Side-by-side is honest — no invented basket size. SM-3 in the PRD validates whether users find this sufficient to make a go/no-go decision.
**Consequences:** The "is it worth it?" verdict is less instant than a single number. If SM-3 fails (users want a dollar figure), Phase 2 options are: fixed assumed basket size, or user-entered intended spend.
**Testing:** SM-3 — test group confirms Discount Display was sufficient for trip decisions.

### ADR-010: Lean R&D Stack (Vite + React + Express + data.json)
**Status:** Accepted
**Date:** 2026-06-09
**Context:** Architecture phase — need a full-stack for R&D validation. Priorities: zero infrastructure cost, zero setup friction, maximum iteration speed for solo founder.
**Decision:** Frontend: Vite 6.3 + React + TypeScript + Tailwind CSS v4. Backend: Express v5 + Node.js + TypeScript (tsx). Storage: data.json flat file. Scraper: Axios 1.17 + Cheerio 1.2. Scheduler: setInterval in Express process.
**Rationale:** Every choice eliminates a dependency that would slow R&D validation. No database migrations, no cloud scheduler, no infrastructure provisioning.
**Consequences:** data.json will not scale past ~50 dispensaries without migration to SQLite. setInterval is not production-grade scheduling. Both acceptable for R&D phase.
**Testing:** R&D validation trip accuracy (SM-1, SM-2).

### ADR-011: Hardcoded Road Distance Lookups (no routing API for v1)
**Status:** Accepted — supersedes ADR-002 for R&D
**Date:** 2026-06-09
**Context:** ADR-002 flagged routing API as required. Architecture phase evaluated cost vs. R&D scale (~20–50 dispensaries, static locations, fixed origin at 98270).
**Decision:** Pre-compute road distance (via Google Maps, once) from zip 98270 to each dispensary and hardcode in `data.json` as `distanceMiles`. No routing API call at runtime.
**Rationale:** Dispensary locations are static. Zero API cost, zero latency, zero failure mode. Ferry exclusion handled at data-entry time (excluded dispensaries never added).
**Consequences:** Adding a new dispensary requires a one-time manual distance lookup. Not suitable if user-variable origin points are added later.
**Testing:** Spot-check computed distances against Google Maps for 3–5 dispensaries.

### ADR-012: EIA API for Gas Price (daily ≤24h refresh)
**Status:** Accepted
**Date:** 2026-06-09
**Context:** PRD OQ-1 — needed a reliable public source for US average gas price. Options: EIA (US govt), GasBuddy (unofficial API, fragile), AAA (no public API, requires scraping).
**Decision:** EIA (Energy Information Administration) public API. Refreshed daily (≤24h) in `refreshGasPrice.ts`. API key stored in `.env` as `EIA_API_KEY`.
**Rationale:** Free, official, stable. Daily (≤24h) cadence is sufficient — gas price fluctuations don't flip go/no-go decisions. GasBuddy/AAA scraping would be a maintenance liability.
**Consequences:** Gas price may be up to 24h stale. Acceptable given SM-2's 15% accuracy margin.
**Testing:** SM-2 — gas cost within 15% of actual trip fuel cost.

### ADR-013: Hardcoded National Average MPG (28 for R&D)
**Status:** ~~Accepted~~ **Superseded by ADR-055** (2026-06-26) — the hardcoded `nationalMpg` default was removed; MPG now comes only from the user's selected vehicle
**Date:** 2026-06-09
**Context:** PRD required a daily-refreshed national-average MPG figure. No reliable live API found for a single fleet-average number (fueleconomy.gov endpoints are vehicle-specific, not fleet-average).
**Decision:** Hardcode `nationalMpg: 28` in `data.json` meta. Update manually if fleet average shifts significantly.
**Rationale:** US fleet average consistently ~28–30 MPG. Satisfies SM-2 (15% accuracy margin). Eliminates a live API dependency.
**Consequences:** Inaccurate for heavy truck owners; precision mode (ADR-003) mitigates this. If users complain math feels off, add a simple "Your MPG" text input later.
**Testing:** SM-2 — gas cost within 15% of actual trip fuel cost.

### ADR-014: data.json + logs.json Flat File Storage
**Status:** Accepted
**Date:** 2026-06-09
**Context:** Need persistent storage for dispensary config, cached deals, gas price meta, and scraper run logs.
**Decision:** Two JSON files: `data.json` (frontend-served data) and `logs.json` (operator-only scraper log). Writes are atomic (write to `data.tmp.json`, rename). `logs.json` never served to frontend.
**Rationale:** Zero cost, zero setup, zero migrations. Sufficient for R&D scale. Separation of concerns: scraper log bloat doesn't affect frontend payload.
**Consequences:** Not suitable for concurrent writes (single-process Node.js avoids this at R&D scale). Upgrade path: SQLite when dispensary count exceeds ~50.
**Testing:** Verify atomic write prevents partial data from being served during scraper runs.

### ADR-015: Single GET /api/data Endpoint with Server-Side Active Deal Filtering
**Status:** Accepted
**Date:** 2026-06-09
**Context:** Need API design for frontend to consume deal data. Active deal status depends on Pacific Time — timezone logic must be centralized.
**Decision:** Single `GET /api/data` endpoint returns `{ meta, dispensaries[] }` with active deals pre-filtered. Server enforces `TZ=America/Los_Angeles` as the first line of `index.ts`.
**Rationale:** Timezone logic in one place (server). Frontend stays stateless — client-side filter is distance only.
**Consequences:** All time-zone sensitive logic couples to the server. Acceptable — this is a feature, not a bug.
**Testing:** Verify Happy Hours that have expired do not appear in API response. Verify Daily Deals expire at Pacific midnight.

### ADR-016: Axios + Cheerio Scraper with Python Microservice Upgrade Path
**Status:** Accepted (refined by ADR-017)
**Date:** 2026-06-09
**Context:** Need to scrape dispensary HTML for deal data. Most target sites serve plain HTML; some require JS rendering (Dutchie iFrame menus specifically).
**Decision:** Axios + Cheerio for plain HTML scrapers. Upgrade individual scrapers to call the Python Scraper microservice (ADR-017) if a site requires a real browser runtime.
**Rationale:** Cheerio is lightweight and fast for plain HTML. The Python Scraper handles browser complexity without bringing Playwright into the Node.js process.
**Consequences:** Sites that load deals via JavaScript will fail silently (empty `Deal[]` returned) until upgraded to call the Python service.
**Testing:** Verify each dispensary scraper returns expected Deal[] before adding to production data.json.

### ADR-017: Python Scraper Microservice for Dutchie/iFrame Dispensaries
**Status:** Accepted
**Date:** 2026-06-09
**Context:** Dutchie iFrame menus cannot be scraped by Axios+Cheerio — menu data is loaded by JavaScript inside an iFrame and is invisible to standard HTTP clients. Happy Time (the primary target dispensary) uses Dutchie for all three WA locations (Mt Vernon, Pullman, Yakima). A working Python Playwright microservice already exists at `C:\Users\erikc\Dev\Scraper` (FastAPI on port 8000), tested against live Dutchie menus.
**Decision:** Dutchie dispensary scraper files in `server/scrapers/` call `POST http://localhost:8000/scrape` on the Python Scraper service via a shared `server/utils/scraperClient.ts` wrapper. The TypeScript scraper file transforms raw GraphQL JSON (`intercepted[].data`) → `Deal[]`. The scraper contract (`export default async function scrape(): Promise<Deal[]>`) is unchanged — `runScrapers.ts` has no knowledge of which tier a scraper uses.
**Rationale:** The Python Scraper encapsulates browser automation, playwright-stealth fingerprint spoofing, and GraphQL network interception. Isolating this complexity in a separate service means Dutchie API changes, stealth patches, and browser engine upgrades never touch the Node.js codebase. The Happy scraper files stay thin — they own only the business logic (GraphQL → Deal transform).
**Consequences:** Dutchie scrapers require the Python service on port 8000. Local dev: start Python service alongside Node.js. Production: both processes must be deployed (Docker Compose at `C:\Users\erikc\Dev\Scraper\docker-compose.yml`). If the service is unavailable, `scraperClient.ts` catches the error and the scraper returns `[]` — existing stale-handling in `runScrapers.ts` applies.
**Testing:** Verify Happy Time Mt Vernon `scrape()` returns non-empty `Deal[]` with Scraper service running. Verify `[]` returned (no throw) when service is down.

### ADR-018: Build-Time Data Copy Script for dist/
**Status:** Accepted
**Date:** 2026-06-09
**Context:** Code review of Story 1.3 found that `tsc` only compiles `.ts` files — `server/data/data.json` and `server/data/logs.json` were never copied to `dist/`, so `dataRoute.ts`'s `__dirname`-relative `DATA_PATH` resolved to a non-existent file in production builds, causing `/api/data` to return 500.
**Decision:** Added `server/scripts/copyData.mjs` (Node `cpSync`/`mkdirSync`, cross-platform) that copies `server/data/` → `dist/server/data/`, run via `server/package.json`'s `build` script (`tsc && node scripts/copyData.mjs`).
**Rationale:** Keeps `__dirname`-relative paths in `dataRoute.ts` valid at the same relative depth in both dev (tsx) and built (`dist/`) environments, without changing the route code itself.
**Consequences:** Any future non-`.ts` runtime asset under `server/` must be added to `copyData.mjs` or it will be silently missing from `dist/`.
**Testing:** Verified end-to-end — built the project, ran `dist/server/index.js` with `NODE_ENV=production`, confirmed `GET /api/data` returns 200 with correct data (previously 500/ENOENT).

### ADR-019: Root package.json start/build Scripts Aligned to dist/server/ Output
**Status:** Accepted
**Date:** 2026-06-09
**Context:** Following ADR-015's `rootDir: ".."` change, `tsc` output moved from `server/dist/index.js` to `server/dist/server/index.js`, but the root `package.json`'s `start` script (`node server/dist/index.js`) and `build` script (bare `cd server && npx tsc`, skipping `copyData.mjs`) were not updated — found during Story 1.3 code review.
**Decision:** Root `start` → `node server/dist/server/index.js`. Root `build` → `npm run build --prefix client && npm run build --prefix server` (delegates to server's own build script, which includes `copyData.mjs`).
**Rationale:** Single source of truth for the server build process lives in `server/package.json`; the root scripts should delegate rather than duplicate/diverge.
**Consequences:** None — root scripts now match actual build output paths.
**Testing:** Verified `npm run build` (root) → `npm start` (root) → `GET /api/data` returns 200.

### ADR-020: Overnight Deal Time-Window Handling in filterActiveDeals
**Status:** Accepted
**Date:** 2026-06-09
**Context:** Story 1.3 code review found `isDealActive` only handled same-day windows (`nowMinutes >= start && nowMinutes < end`). Happy Hour deals spanning midnight (e.g., `22:00`–`02:00`, per ADR-007) would never be active, since `end < start` makes the comparison always false.
**Decision:** `isDealActive` now detects overnight windows (`endMinutes <= startMinutes`) and treats them as active if (today is in `daysValid` AND now ≥ startTime) OR (yesterday is in `daysValid` AND now < endTime).
**Rationale:** `daysValid` lists the day the deal *starts*; the post-midnight portion of an overnight deal belongs to the previous day's entry, not the calendar day it's currently active on.
**Consequences:** None — same-day window logic unchanged; only the `end <= start` branch is new.
**Testing:** Added 3 unit tests to `filterActiveDeals.test.ts` covering: active before midnight, active after midnight (previous day in `daysValid`), and expired the next morning. Full suite: 13/13 passing.

### ADR-021: Age Gate — Single-Button Design, Strict Boolean Check, Dialog A11y
**Status**: Superseded by ADR-036 (2026-06-19) — the strict-boolean check and dialog a11y carry forward; the single-button, no-decline design is replaced by a two-option gate with returnable decline + "Remember me." (ADR-035 first added the decline affordance; ADR-036 made it returnable and added remember-me.)
**Date**: 2026-06-10
**Context**: Story 2.1 implemented the 21+ age gate (`AgeGate.tsx` wrapping App content, persisted via generic `useLocalStorage` hook under `gma_age_confirmed`). Adversarial code review (Blind Hunter + Edge Case Hunter + Acceptance Auditor) found no AC violations but surfaced hardening issues and one product decision.
**Decision**: (1) Single-button gate ("I am 21 or older" only, no under-21 decline path) is the intended design — explicitly dismissed in review. (2) Gate check is strict `ageConfirmed === true`, not truthiness — `JSON.parse(item) as T` in the generic hook is an unchecked cast, so corrupted/hand-edited localStorage values (e.g. `1`, `"yes"`) must not open the gate. (3) Overlay carries `role="alertdialog"`, `aria-modal`, a labelled heading, and moves focus to the confirm button on mount; button contrast raised to `bg-green-700` for WCAG AA. (4) `setValue` wrapped in `useCallback` for stable identity.
**Rationale**: WA-compliance gate is a click-through attestation, not security; one button keeps it frictionless. The strict check costs nothing and closes the only code path where garbage storage data bypasses the gate. Dialog semantics make the takeover screen non-broken for screen-reader/keyboard users.
**Consequences**: Deferred to `_bmad-output/implementation-artifacts/deferred-work.md`: no cross-tab storage sync, no functional-update form on `setValue`, hook ignores `key` changes after mount. None affect the single-key, single-tab R&D use case. Confirmation never expires (persists in localStorage indefinitely) — required by AC3.
**Testing**: 18 client tests passing (parameterized gate-bypass cases, storage-throws branches, focus/dialog-role assertions, setValue identity). `tsc -b` and lint clean.
**Update (2026-06-18, compliance-launch-gate → ADR-035)**: Decision (1) revised. The single-button design is **superseded** — a secondary ghost "I am under 21" action plus a terminal dead-end screen ("This site is for adults 21 and over.") was added per the regulated-content review's defensibility finding. The decline is session-only state (never persisted, never sets `gma_age_confirmed`) so a reload re-shows the normal gate; the affirm path, strict boolean check, dialog a11y, and focus-on-mount are unchanged. See ADR-035.

### ADR-022: Deal Feed — Hook-Only Data Access, Pure Sort Utility, Pinned en-US Timestamp Format
**Status**: Accepted
**Date**: 2026-06-10
**Context**: Story 2.2 added the deal feed: `useDeals` hook (sole fetch path), `sortDeals` pure utility, `formatLastUpdated`, and `DealFeed` owning loading/error/empty/populated states, mounted under the header inside `AgeGate`.
**Decision**: (1) `useDeals` fetches `/api/data` once on mount with `AbortController` cleanup; abort on unmount is swallowed (`err.name === 'AbortError'`) and never sets state — non-OK status and network failure set `error` (string), leave `data` null, no throw. (2) `sortDeals(dispensaries, now)` takes `now: Date` as a parameter (never reads the clock itself) and sorts via tiered keys: timed Happy Hours by minutes-until-end ascending — negative deltas wrap +1440 for overnight windows (e.g. 22:00–02:00, mirroring server-side ADR-020) — then null-window Happy Hours (stable input order), then Daily Deals by `discountPct` descending. (3) `formatLastUpdated` pins `toLocaleString('en-US', …)` → "Jun 10, 7:45 AM" so output doesn't drift with host locale; invalid ISO → empty string. (4) Error state shows a fixed friendly message — raw error text/status never rendered; timestamp footer renders in populated AND empty states only.
**Rationale**: Passing `now` in keeps the sort pure and unit-testable without fake timers. Pinning en-US makes tests deterministic across machines and matches the spec's example format. Hook-only data access enforces the architecture rule (zero `fetch()` in components) ahead of Stories 2.3–2.6 building on the same hook.
**Consequences**: Single fetch per mount — no polling/refresh yet (stale handling is Story 2.6). Minimal deal rows (name — description — % off) are placeholder UI replaced by `DealCard` in Story 2.3. Within-tier order of null-window Happy Hours is input order (unspecified by spec).
**Testing**: 38 client tests passing (18 pre-existing + 20 new: hook success/500/network-reject/abort-on-unmount, all I/O-matrix sort cases incl. overnight wrap, format valid/invalid, four DealFeed render states + sort order + timestamp presence, App feed-region render with stubbed fetch). `tsc -b` and lint clean.

### ADR-023: Deal Cards — Single Time-Window Predicate, 60s Clock, Server-Mirror for Degenerate Shapes
**Status**: Accepted
**Date**: 2026-06-10
**Context**: Story 2.3 replaced the 2.2 placeholder rows with `DealCard` and added a live countdown plus client-side expiry. Adversarial review caught the implementation inventing "end-only deal = since-midnight window" semantics that contradicted the server (which treats ANY null time as day-long-active), and three subsystems (display, expiry, sort) routing degenerate time shapes inconsistently.
**Decision**: (1) One predicate, `hasValidTimedWindow(deal)` (both times present AND parseable), drives expiry, countdown, and sort-tier routing — only fully-valid timed windows compete in the urgency tier, get a countdown, or expire client-side. (2) Every other shape (null, partial, malformed times) mirrors the server's null-time behavior: always shown, never client-expired, sorted with the all-day tier. (3) A single `useNow` hook (60s `setInterval`, cleanup on unmount) is the only clock; the expiry filter runs BEFORE `sortDeals` so expired deals never reach the overnight-wrap heuristic. (4) `DealCard` is purely presentational — window/countdown strings computed in `DealFeed`, passed as props. (5) Window copy ladder: "9:00 PM – 11:30 PM" / "9:00 PM – close" / "Until 11:30 PM" (end-only, display-only) / "Active today".
**Rationale**: Splitting time policy across display/expiry/sort caused the exact disagreements review found (a malformed-start deal sorting as urgent while rendering as malformed and living forever). A single predicate makes disagreement structurally impossible. Mirroring the server for degenerate shapes keeps client and server answering "is this active?" identically — the client tick only ever removes what the server would also drop.
**Consequences**: Deferred (see `deferred-work.md`): long-open tabs resurrect stale deals when their clock window next matches (no refetch is a frozen 2.3 boundary — needs monotonic removal or polling, Epic 3 candidate); no `visibilitychange` resync on mobile; server accepts zero-length windows (`start === end` = 24h-active) — scraper validation in Epic 4 should normalize. Countdown can lag up to ~59s (mount-anchored tick, minute precision) — accepted for R&D.
**Testing**: 82 client tests passing (77 from implementation + 5 review regressions: server-mirror end-only, `hasValidTimedWindow` shapes, "– close"/"Until X" feed derivations, malformed-start tiering). `tsc -b` and lint clean.

### ADR-024: Gas Cost — Pure Formula Module with Shared Validity Predicate, Number-Only MPG Contract
**Status**: Accepted
**Date**: 2026-06-10
**Context**: Story 2.4 delivered the product's core differentiator (ADR-009 side-by-side Discount Display: "35% off — $1.80 to get there"). Review found the MPG-validity rule duplicated between `DealFeed` and `gasCost.ts`, and no guard against a non-finite product reaching display.
**Decision**: (1) `roundTripGasCost(distanceMiles, gasPrice, mpg)` in `client/src/utils/gasCost.ts` is the ONLY home of the formula `(distanceMiles × 2) × (gasPrice / mpg)`; returns null on any non-positive/non-finite input OR non-finite product — callers render the discount alone, never a broken fragment. (2) `isPositiveFinite` is exported and reused by `DealFeed` for the vehicle-MPG fallback so the validity rule has one definition. (3) `gma_vehicle_mpg` contract: the stored value must be a JSON **number**; strings (even `"20"`), booleans, ≤ 0, and garbage silently fall back to `meta.nationalMpg` — locked by test so Epic 3's writer (Story 3.2) must serialize a number.
**Rationale**: Money math scattered across components is how display and calculation drift; null-propagation beats defensive formatting (`$NaN`/`$Infinity` can never render). The number-only localStorage contract is asserted now, while the reader is built, so the Epic 3 writer has a failing test to satisfy rather than a silent mismatch.
**Consequences**: Distance 0 and sub-cent costs are treated as "no gas line" — irrelevant for hardcoded R&D distances (all > 1 mile). `toFixed(2)` half-cent float rounding accepted (estimate with SM-2's 15% margin). Cross-tab MPG staleness inherits the known `useLocalStorage` limitation (deferred since 2.1).
**Testing**: 97 client tests passing (+15 this story: formula matrix math $1.46/$2.05/$3.63, full invalid-input sweep, overflow guard, vehicle/garbage/JSON-string MPG fallbacks, per-dispensary distances, gasPrice-0 degradation). `tsc -b` and lint clean.

### ADR-025: Distance Filter — Whole-Mile Validation with Fallback-Not-Clamp, Shared Range Constants
**Status**: Accepted
**Date**: 2026-06-10
**Context**: Story 2.5 added the distance slider (1–50, default 25, `gma_distance_miles`). ### ADR-034: Live-Scraper Execution — Playwright on GitHub Actions Cron → Authenticated Ingest (Chosen)
**Status**: Accepted (2026-06-18) — **chosen go-live path; supersedes ADR-033** as the topology to build. ADR-033 (paid Render private Docker, ~$14/mo) and the parked home-hardware self-host idea (`_bmad-output/brainstorming/scraper-selfhost-build-plan-PARKED.md`) are both retained as record but **not the path**.
**Context**: Same root problem as ADR-033 — 3 of 4 Dutchie sources show `stale` on live `gmaslist.com` because the Python Playwright scraper POSTs to `localhost:8000`, which isn't hosted; `scraperClient.ts` swallows the failure. A roundtable raised a tempting cheaper primitive: **drop the browser entirely and hit Dutchie's consumer GraphQL endpoint with a plain HTTP POST** (no Chromium, runnable on any free cron). A 30-min de-risking spike (2026-06-18) **falsified** that: Dutchie sits behind **Cloudflare bot management** that blocks on **TLS/JA3 fingerprint**, not just cookies. From Erik's own residential IP, a naive `curl` POST to `https://dutchie.com/graphql` → **403 "Attention Required"**; the same `curl` carrying a live `__cf_bm` cookie + `x-dutchie-session` + full Chrome headers → **still 403** (only the TLS fingerprint differs from the real browser). **Decision**: **Run the existing Playwright scraper on a scheduled GitHub Actions workflow (cron), which POSTs assembled results to a new authenticated ingest endpoint on the Render app; Happy stays on the free plan and serves last-known-good.** Concretely: (1) **Runner** — GitHub Actions free Linux runner (~7GB RAM, runs headless Chromium fine — satisfies the proven browser requirement at $0, with no Render Docker service and no home box). (3) **Store registry** — stores live as config (slug + Dutchie retailer id) in-repo; adding a store is a one-line diff, fan out across stores in a matrix so one store's failure is isolated. (4) **Ingest contract** — new `POST /api/ingest` on the Express app: shared-secret header, normalized per-store payload, server validates shape and writes **last-known-good** with a per-store timestamp; partial success allowed; **never overwrite good data with empty/invalid**. (5) **Stop in-process scraping** — retire the boot/`setInterval` `runScrapers()` on Render (ADR-010); Render becomes read-only over `data.json`/store. (6) **Observability fix (root cause)** — replace `scraperClient.ts`'s silent error-swallow with explicit per-store status (`ok|stale|failed`) surfaced in `/api/data`, plus an Actions job-failure alert.
**Rationale**: The spike proved the browser is non-negotiable, so the question collapses to *where the browser runs cheapest and most reliably*. GitHub Actions wins on every axis the roundtable cared about: **$0** (vs ADR-033's ~$14/mo), **no hardware to babysit** (vs the parked home box, flagged weakest by all four agents), store-registry + parser **fixtures/tests run in CI**, and the scraper is **fully decoupled** from the live site (a scrape crash can't take the page down). It keeps the proven `runScrapers` → `normalizeDeals` → `Deal[]` pipeline (ADR-029/030) — only its *trigger* and *destination* move.
**Consequences**: Inverts the data flow from pull (Render calls scraper) to **push** (runner calls Render) — new ingest endpoint + auth + last-known-good store become load-bearing contracts. Implementation (ingest endpoint + auth + retiring `setInterval`) should run through the normal BMad story flow; the Actions workflow + secret are new infra.

**Status**: Accepted
**Date**: 2026-06-18
**Context**: The UX regulated-content review (`review-regulated-content.md`) logged three "verify with counsel" items the spec left open before public launch: (1) whether republishing scraped retailer ad copy makes the aggregator an "advertiser" under **WAC 314-55-155**; (2) which (if any) WA mandatory-warning statements apply to a non-commerce aggregator; (3) the defensibility of the age gate's no-decline posture (ADR-021). These are genuine legal questions for WA counsel, but each has an engineering posture that is most-defensible regardless of the legal answer and should ship now.
**Decision**: Two tracks. **Counsel track** (Erik + attorney) answers the legal questions and is not code. **Engineering track** (this story) ships the defensible, parameterized posture: (1) **Description sanitization at the single ingest chokepoint** — `sanitizeDescription` runs inside `normalizeDeals` (← `applyIngest` ← `POST /api/ingest`; ADR-034 retired the in-process scraper, so this is the only inbound path). Every `deal.description` is stripped of markup/emoji/control-chars, whitespace-collapsed, and length-capped (80, word-boundary). A whole-word, operator-tunable `DESCRIPTION_BLOCKLIST` of therapeutic-claim and youth-appeal terms **suppresses** the offending copy (blanks the field → DealCard renders badge+discount+window only) but **never drops the deal** (so suppression can't falsely trip the last-known-good stale contract). Whole-word matching avoids false-flagging legit cannabis vocab ("cured resin", "no kidding"); 'gummy' is intentionally not blocked. Descriptions are never rewritten/embellished. (2) **Standing disclaimer footer** (`DisclaimerFooter`, single source of truth, `Notice variant="muted"`, below the feed) always shows the accuracy/affiliation line and the gas-estimate qualifier; the exact WA mandatory-warning text is **staged behind `WA_WARNING_ENABLED` (default `false`)** and surfaces on a single flag flip pending counsel. (3) **Age-gate decline affordance** — secondary ghost "I am under 21" → terminal dead-end screen; session-only, never persists, affirm path unchanged (amends ADR-021).
**Rationale**: The actual regulatory label ("advertiser"? "must warn"?) is counsel's to assign and may stay unsettled, so the code must be correct under either answer — most-defensible by default, trivially upgraded (flip a flag, tune a list) if counsel says "must". The ingest chokepoint is the only correct sanitization site post-ADR-034. Suppress-not-drop preserves the last-known-good invariant. The decline affordance strictly strengthens good-faith posture at near-zero cost.
**Consequences**: Code must not assert a legal conclusion — counsel-decision points are marked `// COUNSEL:` with a reserved, flag-gated slot. The blocklist is a tuning surface Erik owns (false-negatives/positives are expected and adjusted by editing the constant, not logic). WA warning stays dark until counsel enables it. Folds in the review's gas-estimate-qualifier finding (#4, liability framing) at no extra cost.

### ADR-043: Store Visibility Decoupled from Distance — `distanceMiles` is Optional Enrichment
**Status**: Accepted (2026-06-21)
**Context**: Showing each store's deals is the product's core purpose (gas cost is the hook). But 18 batch-resolved Dutchie stores could not appear at all, because two rules coupled *visibility* to *distance*: `applyIngest` only fills deals into a **pre-existing** `data.json` record (no record → `'unknown'` → deals dropped + red CI job), and `normalizeDispensaries` **dropped any record lacking a finite `distanceMiles`** (the data-hardening rule, `deferred-work.md` line ~77). Adding a store therefore required hand-supplying a road distance from ZIP 98270 — backwards from "deals first, distance second, gas third" (Erik, 2026-06-21). This is what reverted the earlier Dutchie wiring.
**Decision**: Make `distanceMiles` **optional enrichment, never a visibility gate.** `Dispensary.distanceMiles` is now `?: number`. `normalizeDispensaries` keeps a record when distance is **absent** (still drops it when **present but** `NaN`/`Infinity`/negative — a corrupt-record signal), and now also requires a non-empty `id` string. The three distance consumers degrade gracefully: `DealCard` omits the distance pill when distance is non-finite (gas line was already suppressed by a null `gasCostText`); the `DealFeed` radius filter never drops an undistanced store; `groupDealsByStore` sorts undistanced stores **last** (treats absent as `Infinity`). The 18 Dutchie dispensary records are seeded (id/name/url, `stale:true`, epoch `lastFetchedAt`, `deals:[]`) so the proven ADR-034 CI ingest path can match and fill them; the stashed `dutchie-stores.ts` registration (`...dutchieScrapers`) auto-adds all 18 to the `storeIds` scrape matrix.
**Rationale**: This is *more* honest, not less (ADR-007/009): a store with no known distance shows no distance and no gas, rather than a fabricated number. It unblocks the core purpose without forcing 18 hand-measured distances, and leaves a clean additive seam for real per-user distance (Deliverable 2 — geocode + ZIP + haversine — which will retire ADR-008/011; see `deferred-work.md`). The present-but-invalid drop is retained so the `.toFixed`/filter/sort paths never meet a poisoned number.
**Consequences**: **Honest interim state:** the 4 original stores still show their fixed-origin distance/gas (ADR-008), the 18 new stores show deals only — resolved when Deliverable 2 geocodes all stores. Deals do not appear at merge: seeding makes records *eligible*; they populate on the next successful GitHub Actions cron (or manual `workflow_dispatch`). A Dutchie store whose cName fails to resolve stays `stale` and simply stays hidden (and reds its per-store CI job — the ADR-034 §6 alert). `dispensary.url` is currently inert (not rendered); the 18 seeded URLs are `dutchie.com/dispensary/<slug>` placeholders pending real values. Does not touch `applyIngest`/`ingestRun`/scrape logic; ADR-038 one-card-per-store and ADR-039 distance ordering hold (undistanced stores extend the order, last).
**Testing**: Updated `normalizeDispensaries.test.ts` (absent-distance kept, present-invalid dropped, id required), `sortDeals.test.ts` (undistanced sorts last, deterministic), `DealCard.test.tsx` (pill omitted, no crash on absent distance), `DealFeed.test.tsx` (undistanced store survives narrowest slider). Full client + server suites + both `tsc --noEmit` expected green; `printStores.ts` emits all 18 new ids into the CI matrix.

### ADR-046: Badge-Anchored Title De-Prefix — Suppress the Redundant "N% off" Stutter
**Status**: Accepted (2026-06-22)
**Context**: Each discount deal card rendered its magnitude twice — once in the styled percent badge (`gma-deal-block__pct` + "off", e.g. "50% off") and again at the head of the title, because the scraped `deal.description` embeds the same phrase ("50% off Select Brands"). The card read as a stutter ("50% off · 50% off Select Brands"), undercutting the deliberate badge-plus-clean-title layout (ADR-040/041, DealCard.tsx). Spec: `_bmad-output/specs/spec-deal-title-discount-dedup/SPEC.md`.
**Decision**: Display-only fix. New pure helper `stripDiscountPrefix(title)` in `client/src/utils/dealView.ts` drops a leading `N% off` phrase via `^\s*\d+(?:\.\d+)?\s*%\s*off\b[\s·:•–—-]*` + defensive `.trim()`. `dealTitle(deal, badgeRendering)` in `DealCard.tsx` calls it **only when the percent badge is rendering** (`discountTier(deal.discountPct)` non-null — badge-anchored); when stripping empties the title it falls through to the existing kind fallback (`'Happy hour'` / omit), **never** the raw description.
**Rationale**: The badge is the canonical place for the magnitude; the title carries only the remainder. Badge-anchored so a discount shown nowhere else is never erased. Case-insensitive on "off" because live data uses "Off"/"OFF" while the badge renders lowercase — a case-sensitive match would silently no-op on real descriptions. Whole-phrase consumption (number + "%" + "off" + trailing separator) avoids a dangling "Off" or leading space. `\b` keeps it off "Offers"/"off-brand". Nothing server-side or at ingest changes — `deal.description` is untouched in memory and storage (ADR-007/009 Honest Math: no data rewritten). Non-percent prefixes ("$5 off", "BOGO") are deferred — the badge is percent-only, so they have nothing to duplicate today.
**Consequences**: On a discount card the magnitude appears exactly once (badge + clean title). No badge → title intact. The badge element and its computation (`discountTier`, `deal.discountPct`) are unchanged. Net new prop on the private `dealTitle` helper; no public/API surface change.
**Testing**: `dealView.test.ts` — `stripDiscountPrefix` across N=10/25/50, casings off/Off/OFF, no-prefix passthrough, "$5 off"/"Offers" left intact, empty-on-phrase-only, input-not-mutated. `DealCard.test.tsx` — badge-anchored strip renders clean title (no dangling "Off"), **no-badge negative case** leaves "50% off Select Brands" intact + description not mutated, empty-strip falls back to kind label. ### ADR-047: Commit-Back Seed — Durable Live Data Across Render Deploys
**Status**: Accepted (2026-06-22)
**Context**: The UI renders `data.meta.lastScraperRun` and the count of `stale===true` stores straight from `data.json` (`DealFeed.tsx:113`/`:93`). Render's disk is **ephemeral**, so every redeploy resets `server/data/data.json` to the **committed seed** — frozen at `lastScraperRun=2026-06-14T16:28:05.534Z` with 17 epoch-seeded `stale:true` stores. PR#24's push-triggered re-scrape POSTs to live `/api/ingest` but loses the deploy-cutover race (PR#28: `[ingestRun] ok` at 16:16:10, then the redeploy discarded the write 35s later); scheduled crons fire only ~every 6h, so prod sat frozen for hours after each deploy → the "Last updated Jun 14" / "17 sources unavailable" flip-flop. Investigation: `_bmad-output/implementation-artifacts/investigations/stale-last-updated-and-unavailable-count-investigation.md`; Sprint Change Proposal 2026-06-22.
**Decision**: Keep the **committed** `data.json` continuously fresh by committing the merged scrape result back to `master` (Correct-Course option 1c). A new `commit-back` job in `.github/workflows/scrape-ingest.yml` (`needs: scrape`, `if: always()`, `continue-on-error: true`) downloads the per-store scrape artifacts and merges them into the checked-out `data.json` via `commitBackSeed.ts` → the **existing `applyIngest`**, then commits only `data.json` to master (`chore(data): refresh seed [skip ci]`, `git pull --rebase` + one push retry). The ephemeral reset then restores a recent seed → deploys become non-destructive. `ingestRun.ts` gains an additive `--emit`/`INGEST_EMIT_DIR` that writes each normalized `IngestEntry` to `<dir>/<store>.json` **before** the POST (one scrape feeds both).
**Rationale**: The seed is built from the raw scraped `Deal[]` via `applyIngest` — **NOT** from `GET /api/data`. `dataRoute.ts:21` pipes deals through `filterActiveDeals` (a time-of-request projection that drops out-of-window happy hours / wrong-weekday deals); round-tripping that lossy view into the source of truth would progressively delete real deals. `applyIngest`'s last-known-good semantics (empty scrape → `stale` flag, deals/`lastFetchedAt` untouched; `lastScraperRun` bumped only when `accepted>0`) make the committed file byte-equivalent to live disk and guarantee no active deal is lost across a cycle. Reading git not prod makes the job deploy-independent (no cutover race). Emit-before-POST means a POST that loses the race (exit 1) still leaves a good seed — and the upload step is `if: always()` so that non-zero step doesn't skip it. **Supersedes PR#24's push-re-scrape as the durability mechanism**; the `push` trigger is retained only for the immediate live refresh between deploys.
**Loop prevention**: `paths-ignore: ['server/data/data.json']` on the `push` trigger breaks the commit→scrape→commit loop **in-repo** (fully in our control); `[skip ci]` is belt-and-suspenders. Does NOT depend on Render's "Ignored Paths" (Erik-owned, optional) — even an unsuppressed Render deploy is at worst one harmless extra deploy onto the just-committed fresh seed, not a loop. `git add` is scoped to `data.json` only (never `-A`) so downloaded artifacts can't break the path-based breaker.
**Consequences**: `permissions: contents: write` for the workflow (commit-back pushes; master is unprotected → GITHUB_TOKEN suffices). "N unavailable" now sticks at its true floor (~11–12 genuinely-unresolved Dutchie cNames) instead of resetting to 17 each deploy — this does NOT lower the floor (separate ADR-043/coverage track). The `accepted>0` guard at `applyIngest.ts:59` is unchanged (correct — "Last updated" should reflect when data last truly changed); commit-back re-commits the live `lastScraperRun`, fixing the visible frozen-date symptom without touching the guard. `alert-gate` (ADR-034 §6) remains the SOLE alert; a permanent push failure surfaces as a `::warning::` without reding the run. `server/out/` is gitignored.
**Testing**: `commitBackSeed.test.ts` — (a) fresh non-empty scrape replaces deals + clears stale; (b) **AC2 invariant** empty entry keeps last-known-good deals + `lastFetchedAt`, flips stale, doesn't bump `lastScraperRun`; (c) absent store untouched; (d) a **time-inactive** (02:00–03:00) deal survives the merge while `filterActiveDeals(noon)` drops it (proves the `applyIngest`-not-`/api/data` correctness point); empty/missing dir → byte-identical no-op; `readEntries` skips malformed artifacts. `ingestRun.test.ts` — emit writes the normalized `IngestEntry`, emits before POST (survives a POST failure), no emit without the flag; `parseEmitDir` flag-over-env. ### ADR-050: Suppress Description-Only Percent on Price-Titled Dutchie Cards
**Status**: Accepted (2026-06-23)
**Context**: `parsePercent` (`_dutchie.ts`) reads the **combined** `name + menuDisplayDescription` text, but the card's displayed title (`Deal.description`) is the `name` ALONE. The `menuDisplayDescription` is not rendered. So a "% off" living only in that (invisible) description badges a card whose visible title shows something else — and when that title is a **price**, the badge directly contradicts it. This is the `$50 Crossroads Ounce` (KushMart) failure: title shows `$50`, a `50% OFF …` in the description made it badge **50% off** in the screenshot, then flipped to no-badge on the next scrape whose description had no `%`. The bare `$50` was never the trigger (`parsePercent` requires a literal `%`); the invisible description was. Flagged as a latent risk in ADR-049's Consequences. **Blast-radius audit across the live catalog (`server/data/data.json`, 2026-06-23): 65 deals, 62 badged; exactly 1 carries a badge percent absent from its visible title — `The Joint – Everett`, title `"Join the Joint: Savings for Everyone!"`, badged 20% from description `"20% OFF ALL ONLINE ORDERS"` — and that one is a GENUINE prose-titled discount. Price-titled badged deals (the `$50` pattern): 0 currently (transient).** So the discriminator is NOT "is the percent in the title" (that bucket holds both the legit Joint deal and the buggy `$50` card) — it is **does the title quote a price**.
**Decision**: Scraper-layer guard, scoped to price-titled cards. New `resolveDiscountPct(name, text)` in `_dutchie.ts`: when the `name` matches `/\$\s*\d/` (states a price) AND has no percent of its own, return `null` — drop the description-sourced percent. Otherwise parse the combined `name + description` as before. `transformSpecials` calls it in place of `parsePercent(text)`. Prose titles with no price (the Joint deal) keep the description percent; a title stating BOTH a price and its own percent (e.g. `"$50 Oz - 50% off"`) keeps that percent.
**Rationale**: Fixes the contradiction at the source (stored `discountPct` becomes correct), unlike the ADR-046/049 display-layer title cleanups — here the data itself was wrong, not just the rendering. Targeting price-titled-without-own-percent is the minimal cut that kills the `$50` contradiction while preserving the one real desc-sourced badge in the catalog: **live blast radius 0** (0 price-titled badged deals today; the Joint deal is prose-titled, untouched). Keeping `parsePercent` reading `name + description` is deliberate — the Joint deal depends on it.
**Consequences**: A price-titled Dutchie special whose only percent lives in the hidden description now renders with no badge (correct — the visible title is a price). A genuine "$50 ounce that is also 50% off" must state the `%` in its displayed title to badge; an operator who wants the badge can adjust the menu title (acceptable — the alternative is re-contradicting the price). This is the first scraper-side (data-layer) percent fix; the title-cleanup rules (ADR-046/048/049) remain display-only. Does not address non-price prose titles whose description percent is wrong/over-stated — out of scope, none observed.
**Testing**: `_dutchie.test.ts` + fixture — added a `$50 Crossroads Ounce` card with `menuDisplayDescription: "50% OFF select ounces"`; asserts `discountPct === null`. Existing card-count tests bumped (5→6 cards, 4→5 deals); the Joint deal's `discountPct === 20` assertion unchanged (proves prose titles still keep the description percent). Server suite green; `npm run build` clean.

### ADR-051: Retry-on-Empty for Dutchie Specials Capture (spurious-stale root fix)
**Status**: Accepted (2026-06-23)
**Context**: The hourly `scrape-ingest` alert-gate (ADR-034 §6) kept reding on 7 stores stale for several runs (`the-joint-everett`, `cannazone-old-hwy-99`, `hangar-420-everett/-west`, `cannazone-bellingham`, `2020-solutions-north-bellingham/-pacific-highway`). Forensic trace of the clean scheduled run 2026-06-23 11:58 UTC: **11** Dutchie stores scraped empty (returned 0 deals), of which alert-gate names only the 7 that had previously ingested real deals (last good ~05:01 UTC, now >6h stale); the other 4 are epoch-seed stores excluded from the persistent-stale check. The empties are NOT blocks/404s/cName errors — `postScrape` logs `[scraperClient]` and sets `success:false` on those, and **zero such lines appear** in the run. The Python scraper returns `success:true` with an **empty `getSpecialMenuCards.menuCards`**: the embed loads, but `menuCards` is empty. Downstream, `applyIngest` (correctly) treats an empty scrape as `stale`, keeps last-known-good, and does NOT bump `lastFetchedAt`, so a store that captures empty silently decays past the 6h alert window. **Manual residential-IP probe of the actual embeds (2026-06-23, production stealth `BrowserManager`, control `kushmart-north` = 6 specials confirms the probe) shows the "empty" is NOT one cause but several:** (1) genuinely specials-less stores — `starbuds-bellingham`, `bud-hut-camano-island`, `cannazone-mt-vernon` returned `[0,0,0]` across 3 loads (nothing to scrape — correctly empty, not a bug); (2) Dutchie-side intermittent specials — `the-joint-everett` ingested a real deal at 05:01 but returned `[0,0,0]` at probe time (its special genuinely comes and goes, e.g. day/time-windowed); (3) a CI-environment gap — `sweet-relief-mt-vernon` returns a stable, valid special (`"To-Go Tuesday" / "25% Off All Online Orders Only"` → a clean `discountPct:25, daysValid:[tuesday]` deal) on `[1,1,1]` from a residential IP, yet has NEVER ingested in CI, implicating GitHub's Azure egress (bot-mitigated empty specials) or a CI-only capture-timing miss — NOT a parse/transform drop (the card transforms fine). The original late-emit capture-race (`dutchieRequest`'s documented hazard) is real but is only the (3)-timing slice, not the whole story.
**Decision**: New shared `scrapeDutchieSpecials(storeId, opts)` in `_dutchie.ts` wraps the `postScrape → transformSpecials` pair every Dutchie store already used, retrying while the result is empty up to `DEFAULT_ATTEMPTS` (3 = 1 try + 2 retries). A non-empty capture returns immediately (no wasted retries on healthy stores); a genuinely specials-less store stays empty across all attempts (cheap — empty scrapes return fast). It never throws — a thrown attempt logs `[scraper:<label>]` and counts as empty, preserving the degrade-to-`[]`→stale contract. All four Dutchie entry points (`the-joint-everett`, `jet-cannabis-everett`, `kush21-everett-evergreen` dedicated files + the config-driven `makeDutchieScraper` in `dutchie-stores.ts`) now delegate to it; the per-file try/catch and direct `postScrape`/`transformSpecials` calls are deleted. `ingestRun.ts` `SCRAPE_TIMEOUT_MS` raised 90s→180s so the backstop can't abort a legitimate 3-attempt sequence (each attempt bounded by scraperClient's own 50s axios timeout).
**Rationale**: Node-layer retry (not a Python `scraper-svc` change) is testable with an injected `postFn`, ships immediately, and keeps the vendored service untouched. Retrying on empty is the minimal mitigation for a capture-timing race without re-architecting the wait strategy (a deeper fix — wait for non-empty `menuCards` inside the service — is possible later but higher-risk). `attempts`/`postFn`/`label` are injectable for unit tests and to keep dedicated-store logs readable (their `storeId` is an opaque embed id/cName).
**Consequences**: Retry is a low-cost mitigation that helps ONLY the capture-timing slice (cause 3-timing): a store whose specials exist but are occasionally captured mid-populate now gets up to 3× the chance per run. The probe (see Context) shows that does NOT cover the other empties: genuinely specials-less stores (starbuds/bud-hut/cannazone-mt-vernon) have nothing to scrape — retry runs 3 fast empties and correctly yields `[]` (negligible cost, no false data); Dutchie-side intermittent specials (the-joint) only ingest when a special is actually live, which is correct; and the `sweet-relief` CI gap — a stable special that CI misses — will be DIAGNOSTIC after deploy: if it starts ingesting `"To-Go Tuesday"` on the next scheduled runs, the cause was capture-timing (fixed); if it stays empty while the residential probe still sees the special, the cause is GitHub's datacenter egress (Azure IP served empty specials), which needs a different fix (residential/proxy egress or a server-side wait-for-non-empty), NOT more retries. So this ADR closes the timing slice and converts the rest into a clean, observable next signal rather than claiming to fix all 7. Latent: a store that legitimately drops all specials still (correctly) alerts after 6h — a real "gone dark" signal.
**Testing**: `_dutchie.test.ts` — new `scrapeDutchieSpecials` suite with a queued/counting fake `postFn`: returns first-attempt deals with no retry; retries past two empty captures then returns populated deals; returns `[]` after exhausting attempts on a specials-less store; treats a thrown attempt as empty and keeps retrying; respects a custom `attempts` count. Server suite 197 green; `npm run build` (client + server) clean. **LIVE-CONFIRMED 2026-06-23 (push run 28037294947, master `32eb2a2`): alert-gate flipped 🔴→🟢, `fresh=10/21 → 18/21`, `persistentlyStale=[7] → []`.** All 7 previously-flagged stores now ingest `ok`, INCLUDING `sweet-relief-mt-vernon` (its stable "To-Go Tuesday" special is now captured) — so cause 3 was **capture-timing, not the Azure-IP egress hypothesis**, which is hereby disproven. The only 3 stores still `stale` (`bud-hut-camano-island`, `cannazone-mt-vernon`, `starbuds-bellingham`) are exactly the probe-confirmed genuinely-specials-less stores — correct (epoch-excluded, no alert).

### ADR-054: Fix silent fractional-ounce mis-parse in `parseGrams` (`1/8oz`→1g bug)
**Status**: Accepted (2026-06-24)
**Context**: The FIRST live `scrape-products` run (PR #32 merged as `e6a4907`; run 28122803634; observation `2026-06-24T19:05:43Z` committed as `5f2f6a9`, served live at `gmaslist.com/api/products`) captured 1665 products across 14 stores. **Rationale**: $/gram is the headline comparison metric for Flower/Vaporizers — a silent 3.5× error on the most common flower denominations defeats the engine's purpose. A targeted fraction branch is minimal and leaves the validated `g`/`mg`/`oz`/bare-number paths byte-identical. Fix-forward chosen over scrubbing the already-committed bad observation (Erik 2026-06-24): it's an R&D/private dataset with no public UI consumer, so the corrected observation simply appends after the bad one in `history`.
**Consequences**: Corrects all future fractional-oz observations. No data-shape change; deals pipeline untouched. The three original Dutchie stores remain excluded (ADR-053). No bare fractions (`1/8` without a unit) appeared in the live dataset, but the new branch handles them too.

### ADR-062: Cross-Store Value Matcher — proprietary same-product price-disparity dataset (A1 keystone)
**Status**: Accepted (2026-06-28)
**Context**: The scraped product dataset (`products.json`, 2461 records / 16 stores) is commodity data any one store already holds. The AI-search/proprietary-data plan (`investigations/ai-search-data-strategy-investigation.md`) identifies item **A1** — matching the SAME product across DIFFERENT stores to emit a cross-store price-disparity fact — as the keystone the cheapest-delivered index, brand matrix, and AI-search surfacing all compose from. Prior investigations proved discount % is a flat storewide promo rate (no per-item signal, `fix6`) and that $/gram is honest ONLY same-product cross-store with quality held constant (`value-analysis` §4). The risk: a sloppy matcher that emits FALSE disparities (comparing different strains or mis-parsed weights) reintroduces exactly the "data that lies" the plan exists to avoid — the output's integrity IS the moat.
**Decision**: A purely additive, read-only matcher over `ProductsFile`. (1) `server/utils/productMatchKey.ts` — `deriveMatchKey(rec)` builds a weight-free identity key `brand|strainToken|strainType|category` (unmatchable → explicit `{unmatched}` bucket, never dropped). `canonicalWeightGrams(option)` reuses `parseGrams` (ADR-054) then **snaps to the nearest standard cannabis weight within 2%** so `1/8oz` (3.54g) and `3.5g` both canonicalize to 3.5g (an eighth is an eighth), while `3.6g` stays distinct. (2) `server/utils/crossStoreValue.ts` — `buildMatchReport(file)` groups by `(identityKey, canonicalWeight)`, takes the latest observation's `specialPrice ?? basePrice`, reduces to the cheapest offer per store, requires ≥2 distinct stores, and emits `Disparity{matchKey,displayName,category,weightGrams,lowPrice,highPrice,spread,spreadPct,storesCarrying[]}` sorted by widest spread%. (3) `GET /api/value/disparities` (`valueRoute.ts`) serves the report private/internal, mirroring `productsRoute`. **Honesty gates:** records flagged `weight-mismatch`/`unparseable-weight`/`unparseable-pack` excluded entirely; same canonical weight only (no cross-weight, no whole-catalog $/gram leaderboard); price is the real price paid, never a discount %.
**Rationale**: **Deviation from the story's literal AC1** ("name token only where brand is null"): the strain/name token is included **always**. Brand+strainType+category+weight alone collides distinct strains (GG4 vs Blue Dream of the same brand) → FALSE disparities, violating AC1's own "different products → different key" clause and the integrity mandate. Differing store name formats only cause UNDER-matching (a safe false-negative) — the bias Open-Q2 chose. The matcher recomputes weight from the option LABEL rather than trusting stored `weightGrams` (some committed observations carry the pre-ADR-054 bad parse), so it is robust to stale data. AC5 audit proves excluded records have ZERO output effect via a full-vs-filtered equivalence assertion on real data.
**Consequences**: New `Disparity`/`DisparityStore` types (additive). New private route `/api/value/disparities`. No change to `Deal`, `filterActiveDeals`, `/api/data`, `_dutchie.ts`, `normalizeProduct.ts`, or the products write path (ADR-043/053 decoupling intact). Live run: 2461 records → 427 weight-mismatch excluded, 0 unmatched → **82 honest cross-store disparities** (e.g. OG Chem 3.5g $15–$30 across 4 stores). Downstream Phases 2–5 (Weedmaps wiring, accrual, legal gates → public SSR surfacing, monetization) remain out of scope and gated on non-engineering decisions — this dataset is private only, on the safe side of the ToS/legal line.
**Testing**: 50 new tests — `productMatchKey.test.ts` (19: key match/no-match/unmatchable, weight snapping), `crossStoreValue.test.ts` (10: spread math, special-vs-base, ≥2-store, per-store-cheapest, flag exclusion, same-weight-only, label unification), `crossStoreValue.audit.test.ts` (18: Phase 0 audit on committed data + parse-contract regression lock), `valueRoute.test.ts` (3). Full server suite **310 green**; client+server `npm run build` clean.

### ADR-063: Cross-store matcher honesty hardening — sold-out exclusion + strain-number preservation (post-merge code review)
**Status**: Accepted (2026-06-29)
**Context**: A code review of the ADR-062 matcher (PR #43, different reviewer pass) surfaced two real defects that let the engine emit a fact that lies — the exact failure ADR-062's integrity mandate exists to prevent. **(1) Sold-out low price:** `buildMatchReport` computed `lowPrice`/`spread` from every priced option, never checking `quantityAvailable`. A reported `quantityAvailable: 0` (sold-out) offer could set the headline low and inflate the spread, advertising savings no shopper can act on. Live `products.json` carries **108 / 2838** latest-obs options at qty ≤ 0 (3.8%) — not hypothetical. **(2) Numeric-leading strain tokens dropped:** `strainToken` filtered every token matching `/^\d/`, intended for weight noise (`1g`, `3.5`, `2pk`) but also deleting genuine strain identifiers — `707 Headband` → `headband`, `9 Pound Hammer` → `pound hammer` — so a numbered strain over-matched its unnumbered sibling of the same brand into a FALSE disparity.
**Decision**: **(1)** Add honesty **Gate 4** in `crossStoreValue.ts`: skip an option when `quantityAvailable !== null && quantityAvailable <= 0`. `null` (unknown stock — scraper didn't report it) is kept; only a *reported* zero/negative is excluded, so the matcher compares buyable prices only. **(2)** Replace the blanket `/^\d/` filter with a `stripMeasurements(name)` pass that runs **before** `norm()` (critical: `norm()` strips the `.` in `3.5g`, splitting it into bare `3`+`5g` that would leak). It removes fractional weights (`1/8oz`), number+unit (`3.5g`,`2pk`,`10ct`,`28g`), and bare **decimal** weights (`3.5`) — but keeps bare **integers**, far more likely a strain id (`707`,`9`) than a unitless weight. A unitless integer weight at worst causes UNDER-matching (the safe bias, Open-Q2).
**Rationale**: Both fixes move strictly toward honesty/under-matching, never over-claiming. Gate 4 mirrors the existing price/weight gates (an unbuyable price is as untrustworthy as a mis-parsed weight). The measurement-strip-before-normalize ordering is the load-bearing detail — filtering digit-leading tokens *after* `norm()` cannot distinguish a split weight fragment from a strain number, which is why the original blunt filter existed.
**Consequences**: No type/route/signature change — purely internal to the two utils. Tightens live output to buyable, correctly-identified disparities. Findings #3 (whole-record exclusion when one option is `unparseable-weight`) and #4 (empty-token same-brand merge) were reviewed and **deliberately left** — both are the documented safe under-match direction and are audit-counted, not silent.
**Testing**: +6 tests — `crossStoreValue.test.ts` (3: sold-out excluded, cheapest-in-stock wins over sold-out, unknown-stock kept), `productMatchKey.test.ts` (3: leading-number strain kept, numbered≠unnumbered no-merge, weight/decimal/fraction noise still stripped). Full server suite **310 → 316 green**; client+server `npm run build` clean.

### ADR-080: Phase 1 technical-SEO foundation — robots.txt + dynamic sitemap.xml over the shipped surfaces
**Status**: Accepted
**Date**: 2026-07-10

## Technical Constraints

- US only, WA-focused; distance is now user-relative (ADR-057) — measured from the visitor's device GPS or typed WA ZIP, not a fixed origin
- Distance = `haversine(user, store) × 1.3` road factor, computed client-side from committed store `lat`/`lng` (ADR-044) + a committed WA ZCTA centroid table (ADR-057); no routing API. Retires the pre-computed fixed-origin `distanceMiles` (ADR-008/011)
- Deal data sourced by scraping public dispensary sites (Axios + Cheerio for plain HTML; Python Scraper microservice on port 8000 for Dutchie/iFrame sites — see ADR-017)
- Gas-cost calc: MPG comes ONLY from the user's vehicle via fueleconomy.gov (ADR-028); the hardcoded national-average default was removed (ADR-013 retired by ADR-055) — no vehicle → no gas figure (distance still shows)
- Gas price: EIA public API (weekly refresh), stored in data.json meta
- All active-deal time logic uses America/Los_Angeles (Pacific Time), enforced server-side
- Browser-based only; user preferences (distance, vehicle MPG, age confirmation) persisted in localStorage
- Web app must be mobile-responsive (primary use case: checking from a phone before getting in the car)
- fueleconomy.gov API returns XML by default — must send `Accept: application/json` header
- data.json writes must be atomic (tmp file + rename) to prevent serving partial data
